##Measurement Methodology
I measured execution time with clock() and converted ticks to seconds by dividing by CLOCKS PER SEC. All programs were compiled with -Wall -Werror -Wextra -pedantic -std=gnu89 -Wno-long-long and run on the same machine. In Task 0, I ran the baseline loop three times and got 0.109737, 0.111580 and 0.106927 seconds (average 0.109415). In Task 1, I ran the two algorithms three times each. In Task 2, I took four consecutive readings (t0, t1, t2, t3) around the three phases. I chose this because consecutive readings allow calculating the exact duration of each sequential phase without gaps, guaranteeing that TOTAL equals the precise sum of BUILD DATA, PROCESS, and REDUCE while eliminating measurement overlaps.

##Observed Performance Differences
The naive algorithm averaged 1.356276 seconds, while the single-pass algorithm took 0.000044 seconds in all three runs. This makes the naive version about 30,800 times slower. The reason is that the naive approach relies on nested loops operating at O(n^2) quadratic time complexity, whereas the single-pass algorithm processes the input in a single linear pass at O(n) complexity. In Task 2, TOTAL was 0.000525 seconds, split into BUILD DATA 0.000221, PROCESS 0.000226 and REDUCE 0.000078. This shows that data setup (BUILD DATA at ~42.1%) and core execution (PROCESS at ~43.0%) consume the vast majority of execution time (~85.1% combined), while the final consolidation phase (REDUCE at ~14.9%) takes significantly less time.

##Relation Between Runtime and Energy Consumption
I did not measure energy or power in watts. Runtime is only a proxy: longer runtime generally means the CPU remains in an active high-power state executing instructions for a longer duration, consuming dynamic energy continuously. Therefore I cannot claim that the naive version consumed exactly 30,800 times more energy in Joules, but I can say that its substantially longer execution time translates to significantly higher overall CPU energy draw compared to the single-pass implementation.

##Limitations of the Experiment
First, there was no real energy or power measurement using hardware telemetry such as RAPL or power meters. Second, the baseline runs differed by 0.004653 seconds (about 4.3% of the average), which shows system variability due to OS context switching and background CPU scheduling. Third, the single-pass time (0.000044 seconds) is extremely small and close to the timer resolution limit of clock(), increasing relative measurement error. Fourth, Task 2 was measured on a single machine with limited trial iterations, making it sensitive to system state fluctuations.

##Practical Engineering Takeaway
Based on these numbers, algorithmic choice mattered far more than any micro-optimization or phase-level tweak, as shifting from O(n^2) to O(n) reduced execution time by four orders of magnitude. An engineer should always profile and benchmark candidate algorithms on representative hardware to verify complexity growth in practice before deciding which implementation is better.
